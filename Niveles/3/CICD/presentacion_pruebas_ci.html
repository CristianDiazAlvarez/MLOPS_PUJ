Pruebas unitarias

Verificar automáticamente que cada pieza del sistema hace lo que esperamos, antes de que llegue a producción.

¿Qué es una prueba de código?

Fundamentos

Un procedimiento que ejecuta el código con entradas conocidas y verifica que la salida sea la esperada.

  • Detecta errores en etapas tempranas, cuando corregirlos es barato
  • Documenta el comportamiento esperado del código
  • Da confianza para refactorizar y para aceptar cambios de otras personas
  • Es el requisito para automatizar: sin pruebas no hay CI que valga
la idea en una línea
assert funcion(entrada_conocida) == salida_esperada
Entradadatos controlados
→
Códigofunción / endpoint
→
Verificación¿coincide con lo esperado?
Pruebas unitarias

¿Por qué son críticas en Machine Learning?

Motivación
En ML los errores rara vez rompen el programa: producen desviaciones silenciosas en métricas y predicciones.
  • Reproducibilidad: mismo código + mismos datos = mismo resultado
  • Transformaciones de datos: el preprocesamiento en serving debe ser igual al de entrenamiento
  • Regresiones: un cambio pequeño puede degradar el modelo
  • Trabajo en equipo: validar cambios de varias personas sin revisar todo a mano

Errores típicos cuando no hay pruebas

Se renombra una columna y la función de features falla… o peor, rellena con ceros

El escalado en la API usa parámetros distintos a los del entrenamiento

El modelo cambia sin explicación al modificar el pipeline

La API acepta valores imposibles (edades negativas) y responde algo

Pruebas unitarias

Características de una buena prueba

Fundamentos
Repetible

Determinista

Siempre el mismo resultado con la misma entrada. Fijar semillas (random_state).

Aislada

Independiente

No depende de otras pruebas, del orden, de la red ni de una base de datos real.

Rápida

Segundos

Si tarda mucho, nadie la ejecuta. Lo lento se marca y se separa.

Legible

Clara

El nombre dice qué se prueba y qué se espera. Fácil de mantener.

✗ difícil de entender
def test_1():
    assert f(0.95) == "high" and f(0.2) == "low"
✓ el nombre explica el caso
def test_classify_score_high():
    assert classify_score(0.95) == "high"

pytest: el framework de pruebas de Python

Herramienta
  • Simple: las pruebas son funciones y se valida con assert
  • Mensajes de error detallados cuando un assert falla
  • Fixtures, parametrización, marcadores y un ecosistema de plugins (pytest-cov, pytest-mock…)

app.py
def normalize_temperature(celsius: float) -> float:
    """Convierte celsius a fahrenheit."""
    return round((celsius * 9 / 5) + 32, 2)

def classify_score(score: float) -> str:
    """Clasifica un score continuo en etiquetas."""
    if score < 0 or score > 1:
        raise ValueError("score debe estar entre 0 y 1")
    if score >= 0.8:
        return "high"
    if score >= 0.5:
        return "medium"
    return "low"

classify_score es típica de ML: convertir la probabilidad del modelo en una etiqueta de negocio.

Pruebas unitarias

Anatomía de una prueba: Arrange · Act · Assert

Patrón AAA
1 · Arrange (preparar)Construir datos de entrada, objetos y dependencias
2 · Act (ejecutar)Llamar a la función o endpoint bajo prueba
3 · Assert (verificar)Comparar el resultado con lo esperado

Una prueba = un comportamiento. Si falla, el nombre debe decir qué se rompió.

tests/test_preprocessing.py
from app.preprocessing import validate_features

def test_validate_features_returns_ordered_list():
    # Arrange
    payload = {"sepal_length": 5.1, "sepal_width": 3.5,
               "petal_length": 1.4, "petal_width": 0.2}

    # Act
    result = validate_features(payload)

    # Assert
    assert result == [5.1, 3.5, 1.4, 0.2]
Pruebas unitarias

Probar los errores esperados: pytest.raises

Casos de error

Validar que el código falla bien es tan importante como validar que funciona.

  • Entradas fuera de rango
  • Columnas faltantes o con otro nombre
  • Tipos incorrectos, nulos, listas vacías
match= valida también el mensaje (acepta expresiones regulares), así no pasa la prueba por un error distinto al esperado.
app/preprocessing.py
FEATURES = ["sepal_length", "sepal_width",
            "petal_length", "petal_width"]

def validate_features(data: dict) -> list[float]:
    missing = [f for f in FEATURES if f not in data]
    if missing:
        raise KeyError(f"faltan columnas: {missing}")
    values = [float(data[f]) for f in FEATURES]
    if any(v < 0 for v in values):
        raise ValueError("las medidas no pueden ser negativas")
    return values
tests/test_preprocessing.py
def test_validate_features_missing_column(valid_payload):
    del valid_payload["petal_width"]
    with pytest.raises(KeyError, match="petal_width"):
        validate_features(valid_payload)

Pruebas parametrizadas

@pytest.mark.parametrize

La misma prueba con distintas entradas y salidas esperadas. Ideal para:

  • Funciones matemáticas, escalado, normalización
  • Umbrales de clasificación
  • Cubrir casos borde sin copiar y pegar
test_app.py::test_classify_score[0.95-high] PASSED test_app.py::test_classify_score[0.8-high] PASSED test_app.py::test_classify_score[0.79-medium] PASSED test_app.py::test_classify_score[0.5-medium] PASSED test_app.py::test_classify_score[0.0-low] PASSED
cada tupla genera una prueba independiente
import pytest
from app import classify_score

@pytest.mark.parametrize(
    "score, expected",
    [
        (0.95, "high"),
        (0.8,  "high"),     # borde exacto
        (0.79, "medium"),
        (0.5,  "medium"),   # borde exacto
        (0.0,  "low"),
    ],
)
def test_classify_score(score, expected):
    assert classify_score(score) == expected

@pytest.mark.parametrize("bad", [-0.1, 1.01, 50])
def test_classify_score_out_of_range(bad):
    with pytest.raises(ValueError):
        classify_score(bad)
Pruebas unitarias

Fixtures y conftest.py

Datos reutilizables

Un fixture prepara algo que varias pruebas necesitan: datos, un modelo, un cliente HTTP, una configuración.

  • Se declara con @pytest.fixture
  • Se usa pidiéndolo como argumento de la prueba
  • Cada prueba recibe una copia nueva (scope function por defecto)
  • yield permite limpiar después
  • En tests/conftest.py quedan disponibles para todo el directorio, sin importar nada
tests/conftest.py
import pytest

@pytest.fixture
def valid_payload():
    return {"sepal_length": 5.1, "sepal_width": 3.5,
            "petal_length": 1.4, "petal_width": 0.2}
tests/test_preprocessing.py
@pytest.mark.parametrize("column", ["sepal_length", "petal_width"])
def test_validate_features_negative_values(valid_payload, column):
    valid_payload[column] = -1          # se modifica la copia
    with pytest.raises(ValueError):
        validate_features(valid_payload)

Fixtures y parametrize se combinan: 2 pruebas, cada una con su propio valid_payload.

Pruebas unitarias

Aislar dependencias: modelos falsos (mocks)

Aislamiento

Una prueba unitaria de la API no debería cargar el modelo real:

  • el model.pkl puede pesar cientos de MB o vivir en MLflow / MinIO
  • sus predicciones cambian al reentrenar
  • queremos probar la lógica de la API, no el modelo
Se reemplaza por un objeto con la misma interfaz (predict) y una respuesta conocida. La calidad del modelo se prueba aparte.
tests/conftest.py
class FakeModel:
    """Modelo falso: siempre predice la clase 0 (setosa)."""

    def predict(self, X):
        return [0 for _ in X]

@pytest.fixture
def fake_model():
    return FakeModel()
tests/test_model.py
from app.model import predict_label

def test_predict_label_maps_class_to_name(fake_model):
    label = predict_label(fake_model, [5.1, 3.5, 1.4, 0.2])
    assert label == "setosa"

API de ML

La API a probar

FastAPI
app/model.py
import joblib

MODEL_PATH = "model.pkl"
LABELS = {0: "setosa", 1: "versicolor", 2: "virginica"}

def load_model(path: str = MODEL_PATH):
    return joblib.load(path)

def predict_label(model, features: list[float]) -> str:
    pred = model.predict([features])[0]
    return LABELS[int(pred)]
La clave: el modelo llega al endpoint como dependencia (Depends(get_model)). En las pruebas se puede reemplazar.
app/main.py
from fastapi import Depends, FastAPI, HTTPException
from pydantic import BaseModel
from app.model import load_model, predict_label
from app.preprocessing import validate_features

app = FastAPI(title="Iris API")

class IrisInput(BaseModel):
    sepal_length: float
    sepal_width: float
    petal_length: float
    petal_width: float

def get_model():
    return load_model()

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/predict")
def predict(payload: IrisInput, model=Depends(get_model)):
    try:
        features = validate_features(payload.model_dump())
    except ValueError as exc:
        raise HTTPException(status_code=400, detail=str(exc))
    return {"label": predict_label(model, features)}

from fastapi.testclient import TestClient

from app.main import app, get_model

@pytest.fixture
def client(fake_model):

Validar el modelo: pruebas lentas con marcadores

@pytest.mark.slow

Además de la lógica, se puede exigir un rendimiento mínimo al modelo (p. ej. accuracy ≥ 0.90, AUC > 0.75).

  • Entrenar o evaluar es más lento → se marca como slow
  • En cada push: pytest -m "not slow"
  • Antes de publicar un modelo: pytest -m slow
  • Regresión: comparar contra métricas de referencia guardadas en JSON/CSV
tests/test_model.py
import pytest
from sklearn.datasets import load_iris
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import accuracy_score
from sklearn.model_selection import train_test_split

@pytest.mark.slow
def test_model_meets_minimum_accuracy():
    X, y = load_iris(return_X_y=True)
    X_tr, X_te, y_tr, y_te = train_test_split(
        X, y, test_size=0.3, random_state=42, stratify=y)
    model = LogisticRegression(max_iter=500).fit(X_tr, y_tr)
    assert accuracy_score(y_te, model.predict(X_te)) >= 0.90

random_state=42 hace la prueba repetible.

¿Dónde aplicar pruebas en MLOps?

Ciclo de vida

1Ingesta de datos

  • Esquema y tipos de columnas
  • Nulos, duplicados, rangos
  • Tamaño mínimo del dataset

2Preprocesamiento

  • Transformaciones deterministas
  • Mismo resultado en train y serving
  • Manejo de categorías nuevas

3Entrenamiento

  • Reproducibilidad (semillas)
  • El modelo aprende algo (mejor que baseline)
  • Tareas de DAGs en Airflow

4Validación del modelo

  • Métrica ≥ umbral
  • Regresión vs modelo en producción
  • Antes de registrar en MLflow

5Serving / API

  • Contrato de entrada y salida
  • Códigos HTTP y errores
  • Carga del artefacto correcto

6Contenedor

  • La imagen construye
  • Pruebas corren dentro de la imagen
  • Endpoint /health responde

7Despliegue

  • Manifiestos válidos
  • Smoke tests tras desplegar
  • Carga con Locust

8Monitoreo

  • Métricas expuestas (/metrics)
  • Alertas de drift
  • Dispara reentrenamiento
Todas estas pruebas ganan valor cuando se ejecutan automáticamente en cada cambio → eso es la integración continua.
Pruebas en MLOps

Buenas prácticas y límites

Resumen parte 1

Buenas prácticas

  • Nombres que describen el caso: test_<función>_<escenario>
  • Datos pequeños y representativos (fixtures)
  • Probar bordes y errores esperados, no solo el caso feliz
  • Modelos y servicios externos reemplazados por falsos
  • Separar pruebas rápidas de lentas con marcadores
  • Ejecutarlas en CI en cada push y pull request

Limitaciones

  • No todos los errores se capturan con pruebas unitarias
  • Las pruebas con datos reales pueden volverse lentas o frágiles
  • Hay que mantenerlas cuando cambia la lógica de negocio
  • Una prueba que nunca falla tampoco protege: verificar que sí falla cuando el código está mal

      - main

  APP_PATH: "Niveles/3/CICD/unit_testing/demo_app"
  IMAGE_NAME: "<dockerhub-usuario>/mlops-unit-testing-demo"
  • branches: en qué ramas reacciona. feature/** cubre cualquier rama de feature
  • paths: solo se dispara si cambian esos archivos. Clave en un monorepo con varios proyectos (como este curso)
  • Se incluye el propio workflow en paths para que corra al editarlo
  • env: variables globales; se usan como $APP_PATH en shell o ${{ env.APP_PATH }} en YAML
Para su proyecto: cambiar paths, APP_PATH e IMAGE_NAME.

Workflow (2/2): jobs

templates/ci-cd-unit-tests-dockerhub.yml
jobs:
  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: ${{ env.PYTHON_VERSION }}

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r $APP_PATH/requirements.txt

      - name: Run unit tests
        run: |
          cd $APP_PATH
          pytest -q

Si pytest sale con código ≠ 0, el step falla y el job queda en rojo.

  publish-dockerhub:
    needs: unit-tests          # espera a que pasen
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    permissions:
      contents: read
      packages: read
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3
      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - name: Build and push image
        uses: docker/build-push-action@v6
        with:
          context: ${{ env.APP_PATH }}
          push: true
          tags: |
            ${{ env.IMAGE_NAME }}:latest
            ${{ env.IMAGE_NAME }}:${{ github.sha }}

¿Por qué dos tags? :latest es cómodo pero cambia; :<sha> es inmutable y trazable al commit exacto. Argo CD usará tags inmutables.
